# ADR-0003 石狩本番・東京復旧と暗号化論理バックアップ

- 状態: 採用（Stage 3。実クラウド検証待ち）
- 日付: 2026-08-16
- 対象要求: `REQ-MVS01-DR-001`〜`REQ-MVS01-DR-005`
- 置換対象: ADR-0002の「東京primary・石狩復旧」という将来記述

## 背景

最重要システム部分はさくらのクラウドへ置き、地域災害で同一リージョンの複数ゾーンが同時に影響を受けても復旧できる必要がある。さくらのクラウド公式マニュアルは、同一リージョン内のゾーン分散をリージョンDRとして推奨せず、東京・石狩のリージョン分散を有効としている。

2026年8月16日時点のオブジェクトストレージCRRは非同期・結果整合であり、石狩第1サイトから東京第1サイトへの片方向だけに対応する。CRR有効化前の既存オブジェクトは自動複製されず、両バケットのバージョニングが必要である。

- https://manual.sakura.ad.jp/cloud/objectstorage/about.html
- https://manual.sakura.ad.jp/cloud/objectstorage/crr.html

## 決定

### 1. リージョン役割

- 石狩を本番リージョン、東京をリージョン災害時の復旧リージョンとする。
- 石狩内の複数ゾーン/ホスト分散は通常の機器・ゾーン障害対策であり、東京復旧の代替にしない。
- 東京はStage 3ではコールド復旧先とし、平常時に書込み可能な第二primaryを置かない。
- GSLB切替は災害責任者と技術責任者の二者承認後に行う。自動切替による二重書込みを避ける。

### 2. 暫定復旧目標

- RPO: 1時間以内。1時間ごとの論理バックアップ完了を基準点とする。
- RTO: 4時間以内。災害宣言から東京APIの整合性確認完了までを測る。
- 目標は事業責任者が正式承認するまで暫定値とする。
- CRRは非同期なので、バックアップ成功だけでなく東京側到達確認を別の監視項目とする。

### 3. バックアップ保護

1. `pg_dump` custom formatを作成する。
2. dumpのSHA-256、取得開始/完了時刻、backup IDを内部manifestへ記録する。
3. manifestとdumpだけをtarへ格納する。
4. バックアップ署名鍵でCAdES/SHA-256署名する。
5. 東京側だけが保有する復旧秘密鍵に対応する公開鍵でCMS/AES-256-GCM暗号化する。
6. `.partial` へ出力してから原子的に確定し、暗号文と外部metadataだけを石狩へuploadする。
7. 石狩から東京へのCRR完了後、東京側のサイズと暗号文SHA-256を照合する。

外部metadataは改ざん検出の信頼根拠ではない。復元時はGCM認証、固定した署名者証明書によるCAdES検証、内部manifestのdump SHA-256をすべて通過させる。

### 4. 鍵と権限の分離

- 署名秘密鍵: 石狩のバックアップ実行主体だけが読める。
- 復旧公開鍵: 石狩のバックアップ実行主体へ配布してよい。
- 復旧秘密鍵: 石狩本番へ配置しない。東京の秘密管理基盤と別管理の緊急保管に置く。
- 信頼する署名者証明書: 東京復旧環境でピン留めする。
- オブジェクトストレージ資格情報: 最小権限を分離し、ソースupload主体へ東京の読取権限を与えない。
- 鍵ローテーション時は旧バックアップを復号できる旧復旧鍵を保持期間終了まで保全する。

## Stage 3で検証すること

- TC-030: 署名済みAES-256-GCMバックアップを生成し、暗号文へ平文sentinelが現れない。
- TC-031: 暗号文の1バイト改ざんを復元前に拒否する。
- TC-032: 本番DB停止後、別データ領域のDBへ復元し、APIデータと監査を照合する。
- TC-033: snapshot時刻、災害宣言時刻、復旧確認時刻からRPO/RTOを計測する。

## 目標ハードウェア構成（初期値）

これは調達確定値ではなく、負荷試験開始点である。

| 場所 | 役割 | 初期仮想ハードウェア | 可用性上の意図 |
|---|---|---|---|
| 石狩 | API ×2 | 各2 vCPU、4 GiB RAM、40 GiB system disk | 別ホスト/可能なら別ゾーン、ローリング更新 |
| 石狩 | PostgreSQL primary | 4 vCPU、16 GiB RAM、100 GiB data + 50 GiB WAL | 最重要データ、外部公開なし |
| 石狩 | PostgreSQL standby（目標） | primary同等 | 同期/準同期方式は負荷試験で決定 |
| 石狩 | Backup worker | 2 vCPU、4 GiB RAM、一時領域は最大DB dumpの3倍以上 | DB資格情報と署名鍵を限定 |
| 東京 | Recovery API ×1 | 2 vCPU、4 GiB RAM、40 GiB system disk | 平常時は書込み不可、復旧時に増設 |
| 東京 | Recovery PostgreSQL | 4 vCPU、16 GiB RAM、復元対象の2倍以上の空き | 別データ領域への隔離復元 |
| 東京 | Recovery control | 2 vCPU、4 GiB RAM | 復旧鍵、署名者証明書、runbookを使用 |

CPU、RAM、ディスクIOPS、接続数は500同時利用者などの仮定で固定せず、Stage 4以降の負荷試験でp95応答時間、DB cache hit、WAL量、復元時間を測って変更する。バックアップ一時領域はdump、tar、署名済みCMSを同時保持するため、少なくともdump見積りの3倍を確保する。

## 採用しなかった案

### 東京本番・石狩復旧

現在のmanaged CRR方向と逆になるため、アプリケーション管理のコピー処理が必要になる。将来、CRR双方向化または東京→石狩対応が提供された場合は、レイテンシ、運用拠点、災害リスク、コストを再評価する。

### CRRだけをバックアップとみなす

論理削除や破損も複製され得る。CRRは運搬層であり、暗号化バックアップ、バージョニング、復元訓練の代替ではない。

### 自動GSLB切替

Stage 3では東京DBが常時同期された書込み系ではない。監視誤検知で切り替えると、古い復元点への書込みやsplit-brainを生むため採用しない。

## 制約と次の判断

- `pg_dump` の時点バックアップなので、バックアップ間の更新は失われ得る。より短いRPOにはWAL archive/PITRまたはリージョン間レプリケーションを追加する。
- オブジェクトストレージupload/CRR試験は実アカウントがないため未実施である。
- ローカルDR試験のRPO/RTOは手順の測定可能性を示すだけで、ネットワーク、プロビジョニング、承認時間を含む実クラウド値ではない。
- 本番化前に石狩の通常時HA、東京の復旧容量、バックアップ保持期間、データ分類、鍵保管、年4回以上の復旧訓練を正式承認する。
