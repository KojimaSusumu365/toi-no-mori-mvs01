# 1. 目的と適用範囲
本方針は、『問いの森 CORE』の開発プロセスを一般の方と共有する際に、何を、いつ、どの形で公開するかを定めます。公開リポジトリ、配布文書、動画、発表、Issue、Pull Request、試験証跡、障害報告、サンプル環境に適用します。
本方針は、公開を妨げるためのものではありません。安全に公開できるテンプレートと説明を積極的に増やし、非公開部分は理由と見直し条件を明らかにします。
# 2. 公開原則
| ID | 原則 | 判断基準 |
| --- | --- | --- |
| PUB-PR-01 | 目的を先に示す | 公開物ごとに対象読者、学べること、利用条件を示す。 |
| PUB-PR-02 | 最小開示 | 理解・再現に不要な実値、識別子、個人情報は除く。 |
| PUB-PR-03 | 合成して公開 | データ、ログ、証跡は合成・匿名化・無害化する。 |
| PUB-PR-04 | 修正を優先 | 脆弱性や事故の攻撃可能な詳細は、修正・緩和後に公開する。 |
| PUB-PR-05 | 由来を残す | 人、AI、外部OSS、資料の寄与とライセンスを記録する。 |
| PUB-PR-06 | 取消可能 | 誤公開時に非公開化、鍵失効、履歴清掃、通知を行える。 |


# 3. 公開区分
| 区分 | 意味 | 例 | 公開条件 |
| --- | --- | --- | --- |
| P0 公開 | そのまま公開可能 | 憲章、用語、一般構成、合成例 | Owner確認、Secret scan |
| P1 無害化公開 | 実値を除いて公開 | IaC、構成図、ログ、test証跡 | 置換・匿名化・二者確認 |
| P2 遅延公開 | 時期を遅らせる | 未修正脆弱性、Incident詳細、製品切替 | 修正・影響確認・開示判断後 |
| P3 非公開 | 原則公開しない | 秘密鍵、Token、本番個人情報、復号手段 | 公開不可。必要者へ最小権限 |


判定ルール  迷った場合は一段階厳しい区分に置き、公開責任者とセキュリティ担当が再評価します。『既に一部で知られている』ことは公開理由になりません。
# 4. 公開する成果物

| --- | --- | --- |

# 5. 公開してはならない情報
パスワード、秘密鍵、API Token、Cookie、Session ID、復旧コード、証明書秘密鍵。
本番・準本番の実IP、内部DNS、管理URL、VPN設定、Firewallの実許可元、クラウドTenant/Account ID。
氏名、住所、電話、メール、学籍・職員番号、給与、健康・障害・相談内容、自由記述などの個人情報。
未修正脆弱性の再現コード、攻撃可能な設定差分、監視回避方法、実運用の防御弱点。
契約で公開を禁止された価格、資料、第三者コード、大学・企業固有情報。
秘密情報が消えていないGit履歴、artifact、container image、debug dump、screen recording。
# 6. 秘密情報と構成値の管理
## 6.1 リポジトリ規則
config.example.json     公開：項目名、説明、dummy値のみ
.env.example            公開：KEY_NAME=replace-me
infra/modules/          公開：再利用可能なIaC template
infra/environments/     非公開：実CIDR、resource ID、接続先
secrets/                作成禁止：リポジトリ内に置かない
## 6.2 取扱い
秘密は承認済みSecrets管理へ登録し、アプリへ実行時注入する。
長期鍵よりWorkload Identity、短期Token、証明書、役割委任を優先する。
Pull Request、CI、container image、test result、chatへの貼付けを秘密検出の対象にする。
誤公開時は、削除より先に鍵・Tokenを失効し、影響範囲と利用履歴を調査する。
# 7. 個人情報・ログ・画面の無害化
## 7.1 無害化手順
公開目的に不要な列・行・期間を削除する。
実在者の値を合成値へ置換し、単純な伏字で原値を推測できないようにする。
correlation ID、tenant ID、URL、時刻、位置情報を再生成または粒度低下する。
スクリーンショットの通知、別タブ、ブラウザ履歴、ファイル名、EXIFを確認する。
自動検査後、別の人が目視し、公開記録へ区分と承認を残す。
## 7.2 公開例
| 項目 | 公開前の扱い | 公開例 |
| --- | --- | --- |
| 利用者 | 実名・メールを除去 | user-demo-017 |
| Tenant | 大学名・契約IDを置換 | tenant-sample-a |
| IP/Host | 実値を予約例へ置換 | 192.0.2.10 / app.example.invalid |
| Token | 値を表示しない | <REDACTED:ACCESS_TOKEN> |
| 時刻 | 必要なら日単位へ丸める | 2026-08-15 |
| 自由記述 | 原文を使わず合成 | 合成した問い本文 |


# 8. 脆弱性の責任ある開示
脆弱性報告は公開Issueではなく、公開前に定める非公開窓口へ送付してもらいます。本草案では実メールアドレスを記載せず、運用開始前の決定事項とします。報告者に認証情報、個人情報、サービス停止、持続的アクセスの取得を求めません。
| 段階 | 処理 | 目標 |
| --- | --- | --- |
| 受付 | 受領番号、対象、再現可否、連絡可否を記録 | 3営業日以内に受領応答 |
| 判定 | 重大度、悪用可能性、影響、暫定緩和を評価 | Criticalは即時招集 |
| 修正 | 修正、回帰、侵害調査、秘密失効、利用者保護 | 重大度ごとの期限を個別決定 |
| 開示 | 修正後に影響、原因、対策、謝辞を公開 | 攻撃容易性を不必要に高めない |
| 振返り | TC、Threat model、Runbook、教育へ反映 | 同種再発の自動検出を追加 |


# 9. インシデント公開
確認中の情報と確定情報を区別し、影響対象、開始・検知・封じ込め時刻を示す。
利用者が取るべき行動を先に示し、責任回避や過度な技術詳細を優先しない。
個人、報告者、担当者を不必要に特定しない。原因は人名ではなく統制と条件で説明する。
法令、契約、捜査、第三者調整で遅延する場合は、遅延理由と次回更新予定を示す。
# 10. ライセンスと知的財産
| 対象 | 推奨案 | 条件 |
| --- | --- | --- |
| 独自ソースコード | Apache License 2.0 | 特許条項を含む。正式公開前に事業判断を承認 |
| 文書・図 | CC BY 4.0 | 出典表示。個人情報・第三者資料は対象外 |
| 合成データ | CC0または個別表示 | 元データを再現しないことを確認 |
| 第三者OSS | 原ライセンス | NOTICE、著作権表示、再配布条件を保持 |
| 商標・名称 | ライセンス外 | 名称・ロゴ利用規則を別途定める |


未確定事項  上記ライセンスは推奨案です。法人化、共同研究、大学契約、特許方針との整合を確認し、人が正式承認するまでは『案』として扱います。
# 11. AI利用の表示と検証
AIが草案、コード、テスト、図、翻訳へ実質的に寄与した場合は、READMEまたは文書管理欄に記載する。
AI出力は権威ある出典ではない。技術仕様、法令、料金、提供地域は公式情報で再確認する。
生成コードは人によるレビュー、ライセンス確認、試験、静的解析、脆弱性検査を通す。
秘密情報、C2/C3情報、契約で禁止された情報を外部AIへ入力しない。
AIによる承認、責任者名の代筆、実在人物の同意の推定を行わない。
# 12. 公開ワークフロー
Ownerが公開目的、対象読者、成果物、公開区分を申請する。
自動検査でSecret、PII候補、依存ライセンス、内部URL、metadataを検出する。
作成者以外が内容、画面、履歴、artifactを目視確認する。
公開責任者と必要に応じSecurity/Privacy担当が承認する。
署名したrelease/tagとして公開し、hash、版、日付、変更内容を残す。
公開後の連絡窓口と取消手順を確認し、指摘を次版へ反映する。

# 14. 誤公開時の初動
公開URLを非公開化する前後に、流出した鍵・Token・Sessionを直ちに失効する。
公開先、fork、download、cache、artifact、search indexへの拡散範囲を記録する。
個人情報・契約情報・脆弱性の種類に応じ、責任者と専門家へ連絡する。
履歴を清掃して再公開し、秘密が再利用されていないことを検査する。
事故記録、原因、再発防止、追加テストを残し、必要な相手へ通知する。
