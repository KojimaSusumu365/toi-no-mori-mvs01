# 1. 目的
本憲章は、『問いの森 CORE』を、一般の方にも追跡できる公開型の開発プロセスで構築するための共通約束を定めます。クラウド経験の多少にかかわらず、要求、判断、実装、試験、失敗、修正を再現可能な形で残し、学習と実システムの品質を両立させます。
本憲章が定めるのは、個々の製品仕様ではなく、開発中に判断が分かれたときに戻る基準です。法令、契約、利用者の安全、個人情報保護、専門家の指摘が本憲章より厳しい場合は、より厳しい条件を適用します。
# 2. ビジョンと価値
## 2.1 ビジョン
大学、図書館、学生、研究者、地域の人々が持つ問い、資料、経験、成果を、安全に結び直し、次の学び・仕事・研究・事業へ受け渡せる基盤をつくります。システムは人の判断を置き換えるのではなく、判断の根拠と責任を見えるようにします。
## 2.2 優先する価値
| 優先 | 価値 | 開発上の意味 |
| --- | --- | --- |
| 1 | 人の安全と尊厳 | 便利さ、納期、費用より優先し、公開停止・訂正・異議申立てを可能にする。 |
| 2 | 約束と証拠 | 要求と試験を同時に定義し、証跡がない実装を完了扱いにしない。 |
| 3 | 小さな完全性 | 機能数を絞っても、認証、監査、復旧、スマートフォン対応を残す。 |
| 4 | 理解可能性 | 一般向け説明と技術詳細を分け、判断理由をADRに残す。 |
| 5 | 可搬性 | 標準技術とIaCを優先し、特定サービスから安全に撤退できるようにする。 |

# 4. 対象範囲と対象外
## 4.1 本憲章の対象
要求定義、基本設計、詳細設計、実装、試験、脆弱性対応、運用設計、DR演習、公開レビュー。
アプリケーション、クラウド基盤、IaC、CI/CD、テストコード、運用手順、公開用説明資料。
試作、閉域パイロット、本番の各段階。ただし段階ごとに承認ゲートを設ける。
## 4.2 対象外または別承認
無制限の一般利用者登録、決済、給与連携、医療・生命安全に直結する判定。
本番個人情報を用いた公開デモ、外部AIへのC2/C3情報送信、実在者を模した試験データ。
未承認のクラウド契約、費用発生、ドメイン取得、本番公開、秘密情報の登録。
# 5. 役割と責任分離

| System Architect | 構成、境界、ADR、可搬性、容量 | 自作設計の無審査確定 |
| Developer | 詳細設計、実装、単体・契約テスト | 自分の変更の単独承認 |
| Quality Engineer | テスト戦略、自動化、探索、証跡 | 要件の事業優先順位変更 |
| Security Reviewer | 脅威モデル、例外、脆弱性、公開安全性 | 事業責任者に代わる本番公開 |
| Operations | 監視、配備、復旧、インシデント対応 | 手順外の恒久変更 |
| Public Reviewer | 再現、指摘、改善提案 | 本番権限、個人情報、秘密情報へのアクセス |


小規模チームの原則  同一人物が複数役割を兼務する小規模段階でも、『作成』と『承認』の記録を分けます。重大変更は、少なくとも別の人による確認を受けます。
# 6. 開発方式：アジャイルVモデル
Vモデルを長期間の一括工程としてではなく、要求と検証の対応関係として使います。2週間を標準とする短いスプリント内で、V字の左側と右側を一周させます。
## 6.1 対応関係
| 左側成果物 | 右側の対応試験 | 同時に決める内容 |
| --- | --- | --- |
| 利用者要求 | 受入テスト | 成功条件、対象者、許容差、証拠 |
| システム要件 | システム/E2Eテスト | 主要経路、性能、復旧、アクセシビリティ |
| 基本設計・脅威モデル | 結合・セキュリティテスト | 境界、失敗注入、悪用ケース |
| 詳細設計・API・DB | 単体・契約・移行テスト | 境界値、例外、冪等性、ロールバック |
| コード | 静的解析・レビュー | 安全な実装規則、依存、SBOM |


## 6.2 スプリント内ループ
要求ID、利用者価値、データ分類、受入条件を登録する。
設計IDと脅威・異常系を記述し、対応するテストケースを先に作る。
最小実装を行い、Unit、Contract、Integration、UIテストを反復実行する。
失敗をDEFとして記録し、原因、修正、回帰テストを同じリンク上に残す。
実行結果をEVIDとして保存し、利用者受入と人の承認を得て完了する。

# 7. Definition of Ready / Done
| Ready（着手条件） | Done（完了条件） |
| --- | --- |
| 要件ID、利用者、価値、範囲、データ分類がある。 | コード、レビュー、対応テストが合格している。 |
| 正常・異常・境界・悪用ケースのTC草案がある。 | REQ→DSN→TC→AUTO/EVID→DEFが追跡できる。 |
| 依存、外部契約、権利、公開可否が明確である。 | Security、Privacy、Accessibilityの観点を通過している。 |
| 合成データ、観測方法、ロールバック案を準備できる。 | 監視、手順、移行、復旧、ロールバックを必要範囲で確認した。 |
| 承認者と受入者が定まっている。 | 人による受入・公開・リリース承認が記録されている。 |


完全性ルール  テスト証跡がない、Must要件にTCがない、Critical/Highの未処理脆弱性がある、復旧手順が未検証である場合は、リリースしません。

# 9. セキュリティ・プライバシー・倫理
本番個人情報、認証情報、秘密鍵、実IP、未修正脆弱性の詳細を公開リポジトリへ置かない。
運用者はMFA、最小権限、短期資格情報を使い、共有IDと公開SSH/RDPを禁止する。
AIへ送る前にデータ分類、目的、同意、PII/Secretを検査し、C2/C3は標準で遮断する。
利用者は公開停止、訂正、退会、異議申立てを行える。AI候補を自動公開しない。
重大脆弱性は修正・緩和・影響確認後に責任ある形で公開する。
# 10. 公開開発と参加
公開は、完成品だけを見せるためではなく、判断と検証を共有するために行います。ただし、公開範囲はQF-PUB-001に従い、透明性を理由に安全を損ないません。
| 参加形態 | 可能な貢献 | 保護策 |
| --- | --- | --- |
| 一般レビュー | 誤り、読みにくさ、再現性、利用者視点 | 個人情報を投稿しない窓口とテンプレート |
| 技術レビュー | 設計、コード、IaC、テスト、性能 | 合成環境、最小権限、レビュー必須 |
| 学生編集員 | 説明、テスト、資料整理、アクセシビリティ | 有給を原則とし、成果をポートフォリオ化 |
| 専門家 | 法務、セキュリティ、大学運用、倫理 | 見解・責任範囲・利益相反を明記 |


## 10.1 行動規範
人ではなく、仕様、証拠、再現手順を批評する。
初心者の質問を排除せず、専門用語には短い説明を添える。
脆弱性、個人情報、自傷・差別・嫌がらせにつながる情報を公開Issueへ投稿しない。
貢献者名の表示、匿名、削除希望を尊重し、無償貢献を当然としない。

# 14. 例外・変更・停止
仕様例外は、理由、影響、代替統制、期限、Owner、再評価日を記録し、期限切れで自動失効させます。緊急変更でも最低限の試験と二者確認を行い、復旧後24時間以内を目安に通常の記録へ統合します。安全、プライバシー、復旧可能性を確認できない場合は、作業または公開を停止できます。
